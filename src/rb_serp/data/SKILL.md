# serp

Всё про конкретные команды есть в самом CLI: `serp` без аргументов —
версия и список команд, `serp <команда> --help` — подробности и примеры.
Этот документ — только то, чего `--help` не скажет. Если CLI запускать
можно, а файлы читать нельзя, этот же текст печатает `serp --ai`.

```bash
```

From the git tag instead:

```bash
uv tool install "rb-serp @ git+https://github.com/bolandeu/rb-serp.git@vX.Y.Z"
```

Replace `vX.Y.Z` with the latest release tag (install from a tag, never a
branch: [the Standard](https://github.com/bolandeu/cli-generator/src/branch/main/skills/cli-builder/reference/standard.md), Install).

Same command on macOS, Linux and Windows; `uv tool upgrade rb-serp`
updates it. Do not run from source unless asked to develop the CLI.

## Правила

- **`--json` у каждой команды.** Разбирать stdout; человеческий вывод не
  парсить. В stdout — только данные, в stderr — диагностика.
- **Провайдеры — очередь.** `--provider a,b` (или `providers` в настройках
  проекта): отвечает первый, остальные — фолбэки по порядку, только если
  предыдущий упал. Без `-p` и настроек проекта — env `SERP_PROVIDERS="a,b"`,
  иначе `xmlstock,xmlriver`. Список провайдеров и что каждый
  умеет — в `serp search --help`.
- **Поиск платный** (провайдер берёт деньги за запрос/страницу), а каждый
  ответ целиком сохраняется в журнал. Поэтому: один раз `serp search`, а
  другие блоки того же запроса — `serp snippets|ads|related|summary ... --cache`
  (бесплатно). Повторный запрос, если свежесть не критична, — тоже `--cache`
  (с `--max-age 7d` при необходимости). Журнал ведётся по провайдерам: блоки
  конкретного провайдера из журнала — с тем же `-p`, что и при поиске. В
  `sources` видно `from_cache`, `fetched_at` и `complete` — `false` значит
  провайдер отдал неполную страницу (меньше результатов, чем должно быть);
  такую выдачу стоит перепроверить позже. `--force` — только если
  пользователь просит свежие данные.
- **Разные блоки — разные команды:** search (позиции), snippets (сниппеты и
  поля), ads (реклама, Яндекс), related (похожие запросы/вопросы, Google),
  summary (сколько нашлось, ИИ-ответ). Журнал — `serp cache info|list|clear`;
  `cache clear` необратим (правило про --dry-run/--confirm ниже).
- **Данные** — в общем PostgreSQL, если задан `SERP_DATABASE_URL` (иначе
  локальная SQLite). `DATABASE_UNAVAILABLE` (код 5) — сервер недоступен,
  платный запрос не делался и ничего не записано; `DATABASE_NOT_MIGRATED` →
  `serp db upgrade` (меняет общую базу — сначала спросить пользователя);
  `db status --json` — ревизия схемы. `db push --dry-run`, затем `db push` —
  отправить новые локальные ответы в прод (`SERP_PROD_DATABASE_URL`; уже
  имеющиеся пропускаются) — запускает только корневой агент tools, остальные
  присылают ему точную команду. Читать данные serp из SQL — только представления
  `serp_v1_*`; у каждого ответа есть `fetched_at` (UTC) — дата получения.
- **Проект необязателен.** Без него работают настройки по умолчанию;
  `serp init --non-interactive` создаёт `.serp/config.toml`, чтобы закрепить
  очередь провайдеров за папкой. Проект ищется вверх от текущей папки или
  задаётся `--project PATH`.
- **`--non-interactive`** для всего, что может задать вопрос: вместо
  зависания будет понятная ошибка.
- **Доступы** — в связке ключей ОС или в переменных окружения
  `SERP_<PROVIDER>_<FIELD>` (например `SERP_XMLSTOCK_USER`,
  `SERP_XMLSTOCK_TOKEN`), никогда в аргументах или настройках. Проверка —
  `serp auth status --check --json`: по каждому провайдеру источник, статус,
  срок и остаток — без значений; код 3, если обязательный провайдер не в
  порядке. Вход — `serp auth login`.
  Никогда не просить пользователя вставить секрет в командную строку.
- **Необратимые команды** — те, у которых в `--help` есть `--dry-run` и
  `--confirm`. Всегда: сначала `--dry-run`, показать пользователю, получить
  явное согласие, потом `--confirm --non-interactive`.
- **Сначала `serp doctor --json`**, если что-то не так: он проверяет
  проект, настройки, совместимость версий и доступы.
- **`serp describe --json`** — весь CLI одним машиночитаемым документом
  OpenCLI (команды, опции, коды выхода, переменные окружения, данные): голый
  документ, без обёртки `{"ok": ...}`.

## Ошибки

Ошибка: `{"ok": false, "error": {"code", "message", "action"}}`.
Порядок: код выхода → `error.code` → `error.action` (конкретная команда,
которая исправит).

    0  успех (пустая выдача — тоже успех, count: 0)
    1  прочее (UNEXPECTED — баг: повторить с --verbose и сообщить; ABORTED — пользователь отказался)
    2  неверные аргументы
    3  нужны доступы              → serp auth login --provider <имя>
    4  проект не создан           → serp init
    5  сбой провайдера (сеть, деньги на счёте, лимиты; повторы уже были) или общая база недоступна → позже или другой провайдер
    6  CLI старее, чем нужно проекту или общей базе → uv tool upgrade rb-serp

Автоматически повторять имеет смысл только код 5.
